# 004: AsyncStorage の採用

**ステータス:** 採用  
**決定日:** 2026-06-02

## コンテキスト

Todo データをアプリ終了後も保持するため、クライアント側の永続化手段を選定する必要があった。サーバーサイド DB は不要で、デバイスローカルに完結する軽量なストレージが求められた。

## 決定内容

`@react-native-async-storage/async-storage` を採用し、Todo 配列を JSON 文字列でキーバリュー保存する。

## 理由

- **Expo との親和性**: Expo が公式にサポートしており、追加のネイティブ設定なしで動作する。
- **シンプルな API**: `getItem` / `setItem` の2メソッドで読み書きが完結し、学習コストが低い。
- **バックエンド不要**: ポートフォリオ用途でサーバーを立てずに永続化が実現できる。
- **オフライン動作**: ネットワーク不要でデータが保持されるため、UX がシンプルになる。

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| SQLite（expo-sqlite） | テーブル設計・クエリ記述が必要で、Todo 程度のデータ量に対してオーバースペック。 |
| MMKV（react-native-mmkv） | 高速だが Expo Managed Workflow では追加設定が必要で、導入コストが高い。 |
| Firebase Firestore | バックエンドサービスの設定・認証が必要で、アプリの複雑度が上がる。 |
| React Context のみ（非永続） | アプリ終了でデータが消えるため、要件を満たさない。 |

## 影響・トレードオフ

- キーバリュー形式のため、複雑なクエリ（フィルタ・ソート）は JavaScript 側で処理する必要がある。
- ストレージ容量や読み書きパフォーマンスに上限があり、大量データには不向き。
- データの整合性保証がないため、保存・読み込みのエラーハンドリングを実装側で行う必要がある。
