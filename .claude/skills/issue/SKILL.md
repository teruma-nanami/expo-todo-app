# Issue 作成

要件定義をもとに、GitHub Issue を作成する。

## パイプライン

- 前提: `/requirements` 完了（要件定義ドキュメントが存在すること）
- 読込:
  - 新規開発・追加開発: `docs/requirements/` + `docs/features/`（あれば）
  - 保守運用: `docs/maintenance/`
- 出力: GitHub Issue

## Instructions

### Step 1: 要件定義の読込

対応する要件定義ドキュメントを読み込む。

### Step 2: パターン判定

`/requirements` で整理した内容をもとに、ユーザーと対話してパターンを確認する。
明確なルールで縛らず、規模感・重さを対話で判断する。

| パターン               | 目安                                                                              | Issue粒度              |
| ---------------------- | --------------------------------------------------------------------------------- | ---------------------- |
| 新規開発               | 新しい機能体系の構築。設計フェーズ（feature-design, db-design, api-design）が必要 | 機能単位で複数Issue    |
| 追加開発               | 既存機能への大きめの追加。設計が一部必要                                          | 機能単位で1〜複数Issue |
| 保守・バグ・エンハンス | 既存機能の改善・修正。設計不要〜軽微                                              | 基本1Issue = 1チケット |

### Step 3: Issue内容の作成

以下のテンプレートに沿って整理し、ユーザーの承認を得る。

```markdown
## 概要

<!-- 何を・なぜやるか -->

## 対応内容

<!-- 具体的な変更点をチェックリストで -->

- [ ] ...

## 前提

<!-- 着手前に必要な条件・依存関係 -->

## 関連ファイル

<!-- 変更対象のファイルパス -->

## 関連Issue

<!-- あれば -->

## ブランチ名

<!-- CLAUDE.md のブランチ規約に準拠: <type>/#<Issue番号>-<kebab-case> -->

## 工数見積もり

<!-- h単位。内訳も記載 -->

## 納期

<!-- 着手予定日・完了予定日を明記 -->

| 項目       | 日付       |
| ---------- | ---------- |
| 着手予定日 | YYYY-MM-DD |
| 完了予定日 | YYYY-MM-DD |
```

**工数見積もり・納期のガイドライン:**

- 実装の複雑度・影響範囲から h 単位で見積もる
- 内訳を記載する（実装: Xh、テスト: Xh、動作確認: Xh 等）
- 不確実性が高い場合はレンジで提示（例: 3〜5h）
- **納期は必ずユーザーと対話して決定する。** 工数見積もりをベースに着手予定日・完了予定日を提案し、合意を得ること
- 納期が未定・未確定の場合でも「未定」のまま Issue を作成しない。必ず仮の期限を設定する

### Step 4: 工数・納期の確認

工数見積もりをベースに、ユーザーと対話して納期を決定する。

1. 工数見積もり（h単位・内訳付き）を提示する
2. 着手予定日・完了予定日を提案する
3. ユーザーの合意を得る。不明な場合は質問して必ず決定する

**納期が決まるまで Issue は作成しない。**

### Step 5: Issue 作成

承認後、`gh issue create` で GitHub Issue を作成する。

- ラベル: パターンに応じて付与（`enhancement`, `bug`, `feature` 等）
- Issue 番号が確定したらブランチ名を最終確定する

## ルール

- 承認なしに Issue を作成しない
- ブランチ名は CLAUDE.md のブランチ規約に準拠
- 工数は必ず h 単位で見積もる
- **納期（着手予定日・完了予定日）は必ず対話で決定する。未定のまま Issue を作成しない**
- 新規開発の場合は設計スキル（`/feature-design` 等）の完了を推奨してから Issue を作成する

## Examples

Example 1: 保守・エンハンスの Issue 作成
User says: "ID41の要件定義ができたのでIssueを作りたい"
Actions:

1. `docs/maintenance/ID41-hearing-description.md` を読み込み
2. パターン確認（保守・エンハンス → 1Issue）
3. テンプレートに沿って整理、工数見積もり
4. 承認後 `gh issue create` で作成
   Result: GitHub Issue が作成され、ブランチ名が確定

Example 2: 新規開発の Issue 作成
User says: "リマインド機能のIssueを作りたい"
Actions:

1. `docs/requirements/` と `docs/features/` を読み込み
2. パターン確認（新規開発 → 機能単位で複数Issue）
3. Issue一覧を提示して分割方針を確認
4. 各Issueをテンプレートに沿って整理、承認後に作成
   Result: 複数の GitHub Issue が作成され、各ブランチ名が確定

Example 3: 追加開発の Issue 作成
User says: "アンケートにCSVインポート機能を追加したい"
Actions:

1. 要件定義を読み込み
2. パターン確認（/requirements の対話で「追加開発くらい重い」と判断）
3. 必要に応じて機能分割を提案
4. 承認後に Issue 作成
   Result: GitHub Issue が作成

## Troubleshooting

Error: 要件定義が存在しない
Cause: `/requirements` を先に実行していない
Solution: 「先に `/requirements` で要件を定義しましょう」と案内する

Error: Issue番号が未確定でブランチ名が書けない
Cause: Issue作成前の段階
Solution: ブランチ名は仮で `<type>/#XXX-<kebab-case>` とし、Issue作成後に確定する旨を記載
