# 要件定義

対話形式で要件を定義し、仕様ドキュメントを作成する。

## パイプライン

- 前提: なし
- 読込: なし
- 出力:
  - 新機能: `docs/requirements/`
  - 保守運用: `docs/maintenance/{ID}-{内容のkebab-case}.md`（1ファイルに要件をまとめる）
- 次: `/feature-design` → `/db-design` → `/api-design`

## プロセス

### 1. ヒアリング（2〜3問ずつ段階的に）

- 機能の目的・背景
- アクター（誰が使うか）
- 主要ユースケース
- 既存機能との関連
- 非機能要件（パフォーマンス、セキュリティ等）

曖昧な回答には具体例を提示する。未定の項目は選択肢を出して一緒に判断する。

### 2. 整理・確認

以下の構造でまとめ、ユーザーの承認を得る:

- 概要（目的・背景）
- ユーザーストーリー（「〜として、〜したい。なぜなら〜だから。」）
- 機能要件（受け入れ条件付き）
- 非機能要件
- 画面・API 一覧（概要レベル）

### 3. 出力

承認後、Markdown で出力する。

- 新機能: `docs/requirements/` に出力
- 保守運用（「保守」「#ID」等のキーワードがある場合）: `docs/maintenance/{ID}-{内容のkebab-case}.md` に出力

出力後「次は `/feature-design` で機能設計を進めましょう」と案内する。

## ルール

- 承認なしにファイル出力しない
- 開発着手に必要十分な粒度（過度に詳細にしない）
- 不明点を残さない
