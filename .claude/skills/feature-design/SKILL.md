# 機能設計

要件定義をもとに、機能一覧・画面フロー・状態遷移・サーバー境界・画面APIマッピングを設計する。

## パイプライン

- 前提: `/requirements` 完了
- 読込: `docs/requirements/`, `CLAUDE.md`（フロント設計原則）
- 出力: `docs/features/`
- 次: `/db-design`, `/api-design`

## プロセス

### 1. ドキュメント読込

`docs/requirements/` と `CLAUDE.md` のフロント設計原則セクションを読んで理解してから開始する。

### 2. ヒアリング（2〜3問ずつ）

- 設計対象の機能範囲
- アクターと認証・認可（middleware / layout / page のどこで弾くか）
- 画面遷移のイメージ
- 状態遷移があるリソースの洗い出し（例: 下書き→公開→アーカイブ）
- 非機能要件（想定件数・ページング・検索・リアルタイム性）

曖昧な回答には具体例を提示する。未定の項目は選択肢を出して一緒に判断する。

### 3. 設計提示（段階的に確認を取る）

**ステップ1: 機能一覧**

| #   | 機能名 | アクター | 概要 | 対応画面 |
| --- | ------ | -------- | ---- | -------- |

→ 確認

**ステップ2: 画面フロー**

Mermaid フローチャートで遷移を視覚化する。→ 確認

**ステップ3: 状態遷移**（該当リソースがある場合のみ）

Mermaid stateDiagram で視覚化する。→ 確認

**ステップ4: ビジネスルール**

機能に関わるビジネスルール（条件分岐・制約・自動処理）を洗い出す。
要件定義から読み取れるものに加え、暗黙のルールがないかユーザーに確認する。

| #   | ルール | 条件 | 結果 | 違反時の挙動 |
| --- | ------ | ---- | ---- | ------------ |

各ルールについて:

- **誰が**（アクター or システム）トリガーするか
- **いつ**（画面操作 / バッチ / イベント）発動するか
- **違反時**にユーザーにどう伝えるか（エラーメッセージ / ボタン非表示 / 自動処理）

→ 確認

**ステップ5: サーバー境界図（フロント実装方針）**

CLAUDE.md の「Server / Client コンポーネント境界」原則に沿って、画面を構成する各要素を Server / Client / URL のどこに配置するかを明示する。

```
例: カテゴリ一覧画面

URL
  └─ ?page=N                            ← ユーザー意図の Source of Truth
page.tsx (Server)
  ├─ searchParams.page をパース
  ├─ fetchCategories(page) 呼出
  ├─ 範囲外は redirect("/admin/...")
  └─ props として下流へ渡す
CategoryListPage (Server)
  ├─ SubNavigation (Client: usePathname)
  ├─ CategoryGrid (Server)
  │   └─ CategoryCard (Server)
  └─ <Suspense>
        └─ CategoryPagination (Client: useSearchParams)
```

判定項目:

- データ取得は Server Component で行うか？
- `"use client"` が必要な「葉」はどれか？
- `useSearchParams` を使う箇所に `<Suspense>` 境界があるか？
- `hooks/` を作るか、作らないか（CLAUDE.md の判断基準に照らす）

→ 確認

**ステップ6: 認証・認可設計**

middleware / layout / page の 3 層のどこで何を弾くかを表にする。

| 層                 | チェック内容               | 失敗時の挙動           |
| ------------------ | -------------------------- | ---------------------- |
| middleware.ts      | 未認証リダイレクト         | `/login`               |
| (admin)/layout.tsx | 管理者権限の確認           | 403 or `/` へ redirect |
| page.tsx           | リソース所有権（必要なら） | 404 or 403             |

→ 確認

**ステップ7: 画面・API マッピング**

| 画面 | 操作 | API エンドポイント | メソッド | 取得タイミング |
| ---- | ---- | ------------------ | -------- | -------------- |

「取得タイミング」列は `Server Component 初期描画 / Client 側の mutation / URL 変更時` などを記載する。

→ 確認

**ステップ8: セルフレビュー（設計ロック前の必須チェック）**

以下のチェックリストを全項目自走で埋め、結果をユーザーに提示する。

| #      | 観点                                                                             | 判定  | 根拠 |
| ------ | -------------------------------------------------------------------------------- | ----- | ---- |
| SEC-1  | 認証・認可の欠落はないか（middleware / layout / page の責務が埋まっているか）    | ✅/❌ |      |
| SEC-2  | 「将来対応」で認可を省略していないか（最低限の pass-through も設計されているか） | ✅/❌ |      |
| SEC-3  | Client Component の条件分岐をセキュリティ境界に使っていないか                    | ✅/❌ |      |
| SEC-4  | `NEXT_PUBLIC_*` に機密情報が乗っていないか                                       | ✅/❌ |      |
| PERF-1 | Server Component をデフォルトにしているか                                        | ✅/❌ |      |
| PERF-2 | N+1 を生まないデータ取得設計か                                                   | ✅/❌ |      |
| PERF-3 | 重い非同期は `<Suspense>` で分割されているか                                     | ✅/❌ |      |
| PERF-4 | 画像・フォントは `next/image` / `next/font` を使う方針か                         | ✅/❌ |      |
| ARCH-1 | `hooks/` を作る判断基準が CLAUDE.md と整合しているか                             | ✅/❌ |      |
| ARCH-2 | `features/` 間の依存が型 import のみで収まるか                                   | ✅/❌ |      |
| ARCH-3 | サーバー境界図と画面・API マッピングが矛盾していないか                           | ✅/❌ |      |
| ARCH-4 | Server / Client の責務が葉に収まり、コンテナが Server のままか                   | ✅/❌ |      |
| UX-1   | URL から状態（ページ・フィルタ）を復元できるか                                   | ✅/❌ |      |
| UX-2   | 範囲外・不正値の正常化（redirect）が設計されているか                             | ✅/❌ |      |
| UX-3   | 空状態・エラー状態・ローディング状態の 3 パターンが設計されているか              | ✅/❌ |      |

❌ がある場合は、該当する設計ステップに戻って修正する。全て ✅ になるまで次ステップに進まない。

→ 確認

### 4. 出力

承認後、`docs/features/{機能名}.md` に出力する。出力する設計書には以下を含める:

- 機能一覧 / 画面フロー / 状態遷移 / ビジネスルール / 画面・API マッピング
- **サーバー境界図**（ステップ5）
- **認証・認可設計表**（ステップ6）
- セルフレビュー結果は **付録: 設計レビュー結果** として設計書末尾に追記する（後続スキルが本文と混同しないよう、見出しで明確に分離する）

次のステップを案内する（`/db-design` or `/api-design`）。

## ルール

- 各ステップで確認を取る
- 承認なしにファイル出力しない
- API のリクエスト/レスポンス詳細はスコープ外（`/api-design` で扱う）
- セルフレビューに ❌ が残った状態で出力しない
- ビジネスルールは後続スキルの入力になる重要な成果物:
  - `/api-design`: エラーレスポンス・バリデーションルールの根拠
  - `/implement`: Action の条件分岐・ガード節の根拠
  - `/test-gen`: テストケース（正常系・異常系・境界値）の導出元
- サーバー境界図と認可設計は `/implement` の直接入力になる。実装時の迷いを設計時点で潰す
