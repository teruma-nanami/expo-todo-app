# 🤖 .claude/agents/ 構成・運用ガイド

## 📌 概要

このディレクトリは、Claude Code（CC）がプロジェクトの各開発フェーズにおいて特定の「専門家（ペルソナ）」として自律稼働するための**カスタムエージェント（拡張モジュール）定義**を格納しています。

開発ライフサイクルを「上流の舵取り（設計・計画）」と「下流の品質防衛（レビュー）」の両面から強力にバックアップする2つのコアエージェントが配置されています。

---

## 👥 登録エージェント一覧

### 1. 🧭 Steering Planner (`steering-planner`)

- **使用モデル**: Claude 3 Opus
- **役割**: 機能開発の要件定義・設計・タスク分割の自動化
- **特徴**:
  - `.steering/YYYYMMDD-<title>/` 配下という隔離されたサンドボックス環境でのみ作業を進行。
  - 各フェーズ（要件定義・設計・タスクリスト）の終了時に人間に「承認」を求める対話ゲート（`AskUserQuestion`）を搭載。
  - `CLAUDE.md` に基づいた Schema Driven Development (SDD) の実装順序をタスクリストに強制適用。

### 2. 🛡️ Code Reviewer (`code-reviewer`)

- **使用モデル**: Claude 3.5 Sonnet
- **役割**: 差分コードの自動静的解析および規約・アーキテクチャチェック
- **特徴**:
  - `git diff` を用いて現在のタスクブランチと `develop` ブランチの差分を動的に特定。
  - 書き込み系ツール（`Write`, `Edit`）を禁止し、純粋な「インスペクター（検査官）」として動作。
  - 重大（🔴）、注意（🟡）、提案（🔵）の3段階でレビュー結果をトリアージ。

## ⚙️ エージェント基本マトリクス

| エージェント名       | 想定モデル              | メインツール                             | 主な制約 / 特権                                  |
| -------------------- | ----------------------- | ---------------------------------------- | ------------------------------------------------ |
| **steering-planner** | `opus` (深い論理思考)   | Read, Write, Edit, Bash, AskUserQuestion | `.steering/` 以外の編集・作成は厳禁              |
| **code-reviewer**    | `sonnet` (高速・高精度) | Read, Glob, Grep, Bash, AskUserQuestion  | `Write`, `Edit` ツールの使用禁止（読み取り専用） |

## 🚀 開発運用フロー（シナリオ）

### 🟢 シナリオA：新しい機能を開発するとき（上流工程）

1. **起動**: 開発者が `steering-planner` を起動し、要件をインプット。
2. **Phase 1 (要件)**: 自動調査の後、`1-requirements.md` を作成して人間へ承認を求める。
3. **Phase 2 (設計)**: 承認後、アーキテクチャに準拠した `2-design.md` を作成し、再度承認を求める。
4. **Phase 3 (タスク)**: 実装順序に従った `3-tasklist.md` を作成。承認後、人間はこれに沿って無駄なく実装を進める。

### 🔴 シナリオB：コードをコミット/PR提出する前（下流工程）

1. **起動**: 実装完了後、Pushやマージの前に `code-reviewer` を起動。
2. **自動差分検出**: 自動で `origin/develop` との変更ファイルおよび内容を特定。
3. **規約チェック**: `CLAUDE.md` の層の責務、不要な try-catch、二重ガードの禁止、テストの有無を徹底チェック。
4. **修正・提出**: 出力されたサマリー（🔴重大項目など）を確認・修正してから、安全にコミット/Pushへ移行。

## 🛠️ メンテナンスと拡張について

- **新規スキルの追加**: 本ディレクトリ配下に新しいフォルダまたは `.md` ファイルを作成し、フロントマター（`---` で囲まれた設定部分）を定義することで、CCに新しい人格・役割を学習させることができます。
- **普遍性と固有ルール**: プロジェクト共通の普遍的ルール（例：二重ガードの禁止など）はエージェントに直接組み込み、案件固有のコンテキスト（Figma仕様など）は `CLAUDE.md` や `docs/` 側に切り分けて参照させることで、この `agents/` ディレクトリ全体の汎用性を高く保ちます。
